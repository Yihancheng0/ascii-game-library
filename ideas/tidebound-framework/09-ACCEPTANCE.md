# 09 · 分阶段验收与证据要求

<a id="QA-01"></a>
## 9.1 QA-01：按门槛递进，不用总分掩盖基础失败

| 门槛 | 审查对象 | 必须回答 | 失败后退回 |
|---|---|---|---|
| G0 范围与来源 | 任务卡、规则、参考、许可 | 做什么，什么没做，证据从哪来 | 定义任务 |
| G1 结构 | 轮廓、体块、承托 | 不靠特效和标签能成立吗 | 造型 |
| G2 字符与明暗 | 多视距静态、灰度、无特效图 | 字符是否表达形体 | 材质/采样 |
| G3 动作 | 正常速度、逐帧、转向/中断 | 连接与动力是否连续 | 姿态/状态 |
| G4 环境联系 | 光、水、接触、遮挡 | 是否确实处于这个空间 | 共享系统 |
| G5 场景与操作 | 真实输入、目标与反馈 | 能理解、能执行、能恢复吗 | 交互/构图 |
| G6 集成与设备 | 回归、存档、性能、UI | 在目标设备和入口可靠吗 | 集成 |
| G7 审阅结论 | 证据、限制、用户意见 | 哪些范围获认可，哪些仍待定 | 明确范围 |

不采用“总分 80 就过”这样的补偿机制。穿模、无法完成、存档损坏、未经支持的完成声明不能由好看的截图抵消。G7 的用户审阅不代替 G1–G6 的执行者自查。

<a id="QA-02"></a>
## 9.2 QA-02：不同证据只能证明对应事情

| 证据 | 可以证明 | 不能证明 |
|---|---|---|
| 静态截图 | 一帧构图、明暗、遮挡 | 动作稳定、帧率、操作可用 |
| 离线真实引擎录像 | 指定输入和步进下的画面变化 | 原生浏览器性能、DOM 布局 |
| 自动行为检查 | 明确断言的状态和恢复关系 | 玩家理解与主观美感 |
| 浏览器实际操作 | 对应设备上的输入/页面表现 | 所有设备性能 |
| 用户试玩 | 该玩家在该范围的理解与偏好 | 尚未玩的章节也通过 |
| 源码审查 | 指定缺陷的实现依据 | 运行时一定出现或已消失 |

录像需标注实际/离线、帧率、模拟时间、版本、是否预置状态、是否剪辑。录成 20 fps 不等于游戏只能 20 fps，也不能据此说游戏稳定 60 fps。

<a id="QA-03"></a>
## 9.3 QA-03：用固定场景重复对照

场景索引位于 scenarios.json。本规范建立的场景尚未执行；历史测试只作为旧证据，不自动填入新场景为 passed。

| 场景 ID | 具体操作 | 核心检查 |
|---|---|---|
| SC-SHAPE | 关闭标签、眼睛装饰、特效；近中远观察 | 岛鱼、船鱼、灯鱼主形成立 |
| SC-CHAR | 固定灯与姿态，拖动镜头并改变采样层级 | 字符比例、明暗、字格连续 |
| SC-PAN | 鱼头移出四边，身体/尾迹仍留屏内，再返回 | 裁切不使整层突然消失 |
| SC-TURN | 大鱼沿岸转弯、加速、减速、取消追踪 | 全身连接、避岸、质量感 |
| SC-DEPTH | 鱼穿过栈道下方、岸旁、船后 | 正确遮挡，无透明掩饰 |
| SC-LAMP | 靠近、关注、照明、走远、受阻、栖息 | 生物动作与共同光照 |
| SC-ISLAND | 同一地标观察完整呼吸，再步行经过 | 身体/水线/附着物/碰撞一致 |
| SC-DOCK | 从多个合理方向靠泊、上下岸、取消 | 不被栈道卡住、不传送到非法点 |
| SC-GILL | 完整协作；每阶段中断与返回 | 条件可读、结构变化、恢复 |
| SC-SAVE | 关键状态保存/重载、损坏档、演示入口 | 状态一致、旧档不被污染 |
| SC-WORLD | 分区边界往返、跨区巨物、远坐标 | 稳定生成、持久改动、无接缝 |
| SC-WEATHER | 平静到天气事件再消退；关闭闪光 | 多系统响应与信息等价 |
| SC-UI | 首次进入、停滞、帮助、暂停、窗口变化 | 可发现、可读、不遮主目标 |
| SC-FISHING | 试探、咬合、主动操作、脱钩、结果 | 操作有因果，结果有用途 |
| SC-PERF | 目标设备固定路线与事件峰值 | 帧时间分布、输入延迟、质量档 |
| SC-DOC | 文档链接、编号、状态、版本与公开内容 | 规范可用、无虚构通过 |

每次任务按影响范围选场景，不要求修一个文档跑全游戏。改变坐标、深度、保存等共享系统时扩大覆盖。原鱼相关场景作为保护性对照，不能只测新增对象。

## 9.4 视觉审查怎么写

先逐项回答“能否看出、哪里断了、在什么动作下”。再作整体判断。建议审查表包括轮廓、体积、字符方向、尺度、光照、接触、动作连续、留白和反馈可读性；不设自动美术分数。

对每个失败附版本、场景、时间点、截图或片段、预期和实际。提出最小原因假设与下一次对照方法。比如“背景像贴纸”应细化为“岩面受光不随灯移动，浸水边界未响应波纹”，而不是笼统要求“更精美”。

<a id="QA-04"></a>
## 9.5 QA-04：不能以缺少环境为由伪造验收

浏览器、设备或素材不可用时，完成仍可进行的独立检查，把缺失项写为 blocked 或 pending，说明具体缺口。离线通过可以交付供审阅，但完成声明必须限定范围。

用户明确喜欢某条鱼或某个镜头时，只记录对应范围。不能把“港湾稍微好看”升格为整版美术通过。执行模型自己的审查、另一模型的审查和用户审查分开保存；本轮无额外用户授权，不自动调度多代理。

<a id="QA-05"></a>
## 9.6 QA-05：交付包必须可追溯

运行提交、构建产物、截图、录像、测试报告和说明使用同一版本身份。若录像来自更早版本必须明确。每份证据记录路径/链接、生成方式、场景、时间和限制。

最小交付包括：实际改动；未做内容；执行的检查与结论；待验收项；已知缺陷；回滚位置；版本与文档入口。演示录制只能辅助理解，必须同时提供真实可操作入口。

## 9.7 缺陷等级与处理

阻断：无法推进、严重穿模/分体、存档破坏、错误授权发布、关键反馈失效。进入下一阶段前处理。

显著：主体僵硬、环境像独立平片、提示难发现、遮挡偶发错误、镜头抖动。不能包装为已精修完成；可以明确交付修复中的样片。

打磨：不影响基本理解的小节律、次要细节、局部装饰。记录优先级，避免无休止微调拖住真正阻断项。严重度由影响和复现确定，不能为了赶进度自行降级。

## 9.8 本规范本身如何验收

检查用户反馈覆盖、规则是否可操作、引用是否成立、现有与目标是否混淆、待定是否被偷写成定值、模板是否能独立形成任务。校验脚本只负责结构一致性；完整内容仍需人工阅读。规范通过结构检查不等于游戏通过这些门槛。
